# Build log

Real numbers for the case study. One entry per PR / work block.

> **About this repository's history.** This copy starts from a single commit. The work was done in a private repository as 16 pull requests with tests (the PR numbers in this log refer to them), and that history was not carried over. The times in this log come from that history.

**How the numbers are measured**
- *Hours*: wall-clock time of the Claude Code session, from session timestamps (the owner's review time is not included).
- *Claude Code usage*: this session runs on a Team plan, so there is no per-token invoice. I record the context-window size (tokens in the session) and the plan-limit percentage reported by the app at the time of the entry.
- *App API cost*: money spent on the Anthropic API by the assistant itself (answers, eval judge). Taken from `audit_log.cost_usd` and `eval_results.cost_usd` once the app calls Claude. Until then it is $0.
- *Cloudflare cost*: all resources used stay inside free/included limits unless stated otherwise.

These numbers describe building a demo on invented data. They are not an estimate for a client project; see "What these build numbers are, and are not" in `CASE_STUDY.md`.

### PR 5: ingestion and role-enforced retrieval (22:32 to 22:38 local)
- Schema for documents, chunks and a full-text index (FTS5, trigram tokenizer: substring matching copes with Polish inflection, diacritics ignored). Chunker splits by heading: 36 documents become 219 chunks of 6 to 7 sections each.
- Ingestion service: chunk, flag suspicious text, redact, embed, write to D1 and the vector store. Idempotent (a content hash skips unchanged documents), recovers from a failure half-way, deletes vectors of removed sections, works out which version of a document is the latest. Vectors are optional: without the Workers AI and Vectorize bindings it indexes for full-text search only, so local development needs no cloud resource.
- **Permissions live in `src/worker/retrieval/store.ts`.** Every read function takes the role and filters by access label inside the SQL statement; a role with no access runs no SQL at all; a forbidden document looks exactly like a missing one. The vector query gets the same filter from the same policy, and ids it returns are re-checked in SQL, so a faulty or compromised vector store still cannot leak a chunk (tested with a deliberately leaky fake).
- Mandatory permission tests: 5 roles-with-no-access plus 4 real roles, each asked 30 different questions, plus a matrix of every chunk against every role (219 chunks x 9 roles), plus hostile search text (SQL fragments, FTS syntax).
- Mutation check: making the SQL label clause always true turned 13 tests red; removing only the SQL re-check after the vector search turned exactly the one test built for it red.
- Ops endpoints (`/api/ops/*`) need a bearer token, are off if none is configured, and are not opened by any user session, admin included. `npm run ingest` loads the corpus through them.
- Verified on the real Cloudflare SQL engine (local workerd), not only in unit tests: migration applies, FTS finds "urlop" in the leave policy, 219 chunks in both the table and the index, 3 old versions, 1 flagged chunk, a second ingest run changes nothing.
- One of my own tests was wrong (a multi-word query matches any chunk with any word, so it could not prove a section was gone); I corrected the test, not the code. `sqlite_version()` is blocked in D1, which is irrelevant.
- Tests: 193 passing (was 107).

### PR 8: agentic mode (12:57 to 13:03 local, from the branch creation time)
- The model drives its own search with three tools: `list_documents`, `search_text` (FTS5) and `read_section`. A loop of at most 6 model calls; the last call is sent with `tool_choice: none` (the only tool_choice besides `auto` that Sonnet 5.5 accepts), so a model that keeps searching still has to answer. Medium effort in this mode (low in vector mode).
- **Both modes now share one answer pipeline** (`ask.ts`): same limits, same redaction, same citation check, same refusal rules, same audit row. Only how the passages are found differs (`vectorMode.ts` or `agentic.ts`). Agentic mode needs only the model and the database, no embeddings.
- Permissions: each tool wraps a role-enforced function from `retrieval/store.ts`. The role comes from the session through the tool context. The tools do not even offer a role, user or permission parameter (a test checks the schemas), and a `role` or `is_admin` field the model adds anyway is stripped and ignored. A forbidden document looks exactly like a missing one.
- Loop mechanics that the API requires, each covered by a test: assistant turns are sent back exactly as returned (thinking blocks included); all tool results of one turn go back in one user message; citation indexes count `search_result` blocks across the whole conversation, so the loop records every passage in order; a repeated identical call gets a note instead of new passages; a tool that throws or gets bad input returns an error result and the loop continues.
- Chat UI: a switch between vector and agentic search, and a collapsible "How it searched" list (tool, what was asked, how many results).
- Tests: 322 passing (was 265). 31 for the tools, 26 for the loop and the HTTP route, plus the updated shared tests.
- Mutation check: reading the role from the model's tool input turned 1 test red; not switching off tools on the last step, 1 red; not recording tool passages for citation lookup, 4 red. **One mutation survived:** removing the redaction of tool input before it runs changed no test, because that input is already redacted where it leaves (audit log and answer shown to the user), and the query itself only reads the local database. The extra redaction was dead code, so I removed it and kept the single boundary rule.
- Verified in a real browser with a canned `/api/ask` answer: switch, steps list with a result count and an error badge, citation and source link. **Not verified with the real model:** the loop has only run against a scripted fake, so how well Claude uses these tools (how many calls, how good the queries are) is unknown until the first real run. The prompt tells it to write Polish words with Polish letters, because of the ł limit of the full-text index.
- Claude Code usage at the end of the entry: about 771k tokens in context (77% of the 1M window), 5-hour plan limit 38% used.

### PR 11: evaluation set and runner (14:52 to 14:59 local, from the branch creation time)
- **40 questions** in `eval/cases.json`: 22 answerable (Polish and English, all four roles), 2 with personal data, 3 with conflicting versions, 2 injection attempts, 6 blocked for the asking role, 5 out of scope. Every expected fact carries the exact phrase from the document that proves it, and a test checks that each phrase really is in that document, that every expected document exists and is readable by the asking role, that refusal cases expect no document, and that the "must not appear" strings of the blocked cases exist only in documents the role cannot read. So a wrong expectation cannot make a good answer look bad.
- **What is measured.** Four checks without a model, repeatable and free: the right document was retrieved, the citations point to an expected document the role may read, refused exactly when it should be, and none of the forbidden strings (restricted facts, personal data, the injection canary) appears in the answer. Four judged by a model with a fixed rubric: faithfulness to the cited passages (1 to 5), key facts covered, older version mentioned for conflicts, and whether an injected instruction was followed. The judge is `claude-opus-5-5`, deliberately not the model that writes the answers, so a model does not grade its own work. The judge sees only the cited passages, redacted like everywhere else, and gets one retry if its reply is not valid JSON. If it fails twice the case keeps its four deterministic scores and the row says why.
- **Endpoints** (token only): `POST /api/ops/eval/run`, `POST /api/ops/eval/case`, `GET /api/ops/eval/runs[/:id]`. A case runs through the same `ask()` as a visitor, as the case's role, marked `source=eval`, outside the daily limits. A (run, case, mode) that already has a row is returned as it is, so an interrupted run can be resumed without paying twice. An assistant failure is stored as an error row instead of stopping the run.
- **Runner:** `npm run eval -- --target <url>` (3 cases at a time; `--dry` prints the cost estimate, `--only`, `--modes`, `--resume`, `--out`). It writes `EVAL_REPORT.md` (both modes side by side, per category, failures with the judge's note, cost and latency, models, git sha) and exits with an error if any blocked case was not refused. The dry run estimates about $3.04 for 40 cases in both modes including the judge. **No real run has been made yet**; it needs the owner's approval, and the live Worker does not have this code yet.
- Tests: 375 passing (was 341): the case file against the corpus (5), scoring, judge and report (15), the endpoints (14, including the token on every route, resume, a leak, a wrong citation, a judge that fails, an assistant that fails, personal data redacted before the judge).
- **Mutation check, 13 changes:** 9 turned a test red at once. Three survivors were real gaps and got tests: not redacting the passages shown to the judge, counting all judged facts instead of only the confirmed ones, and dropping the readable-by-role check from the refusal branch. One survivor was dead code and I removed it (a separate replacement of the non-breaking space, which `\s` already covers). One survivor stays on purpose: the synthetic eval user is `is_admin: false`, and flipping it changes nothing observable, because nothing in the answer pipeline reads that flag for document access.
- A mistake of mine, caught by the test and not by running anything paid: I used "8 500" as a forbidden string for the salary question, but it also appears inside every phone number (`+48 500 ...`) and in the band below. Now "11 500", which exists only in the HR document.

(1) The cited passages were handed to the judge in database order, not citation order, so "[1]" in the answer was not passage 1 for the judge (20 of the 80 judge notes mention swapped or mismatched citations, and the 2 scores below 4 that have no other cause are exactly the vector-mode conflict answers where the judge read the old and new version the wrong way round).
